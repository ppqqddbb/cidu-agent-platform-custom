# 租户多应用接口管理与智能体权限方案

## 1. 背景与目标

当前系统需要支持“一个租户管理多个第三方应用”，并让智能体可根据用户问题自动选择应用与接口调用，最终返回结果。  
关键挑战是：Dify 不直接掌握第三方应用登录态与用户权限，需要在不破坏 Dify 现有能力的前提下完成权限透传与可控调用。

本方案目标：

1. 支持不同租户注册多个第三方应用（应用实例维度）。
2. 支持每个应用下管理多个接口，支持 OpenAPI 导入 + 人工确认。
3. 支持智能体按“应用 -> 接口”自动决策调用。
4. 支持用户级/租户级/应用级权限语义，避免权限误用。
5. 支持前端直连 Dify 与 BFF 中转 Dify 两种接入方式。

---

## 2. 已确认约束（冻结）

1. 第三方应用类型不确定，目标是“都要支持”。
2. 前端直连 Dify 与 BFF 中转 Dify 两种方式都要支持。
3. 行/字段级数据权限由第三方应用侧决定，Dify 不做数据权限裁剪。
4. 接口管理支持 OpenAPI 导入并人工确认。
5. 不强制所有调用都经过网关（允许 direct 模式）。
6. 第三方不支持用户级鉴权时，允许降级调用。
7. 租户管理员注册应用不需要审批流。
8. 应用建模采用“第三方系统实例维度”（不是产品类型维度）。

---

## 3. 总体架构

### 3.1 核心组件

1. `Tenant App Registry`（租户应用管理）
   - 管理租户下多个应用实例。
   - 管理应用说明、用途、状态、调用模式、凭据绑定。
2. `Tenant API Registry`（租户接口管理）
   - 管理应用下接口清单、用途说明、风险等级、必需权限。
   - 支持 OpenAPI 导入 + 人工修订版本管理。
3. `Tool Gateway`（统一工具网关）
   - 智能体调用第三方接口的推荐入口。
   - 负责权限校验、令牌交换、审计记录、适配路由。
4. `Credential Broker`（凭据代理）
   - 统一处理 OAuth2/OIDC、API Key、自定义签名等认证方式。
5. `Adapter Runtime`（第三方适配层）
   - 每类第三方协议一个适配器，统一对外调用契约。
6. `Dify Agent`
   - 负责意图理解、工具选择、结果组织。
   - 不直接持有第三方用户登录态。

### 3.2 设计原则

1. Dify 负责“编排与推理”，网关负责“鉴权与调用”。
2. 应用/接口元数据是智能体可解释能力的唯一来源。
3. 同一调用必须可追踪到租户、用户、会话、应用、接口、权限级别。
4. 允许 direct 模式，但要明确风险与权限级别标签。

## 5. 权限与身份方案

### 5.1 Auth Context Token（统一上下文令牌）

由业务系统签发短时令牌，传给 Dify 并在工具调用时传递给 Gateway。建议字段：

1. `sub`（user_id）
2. `tenant_id`
3. `session_id`
4. `roles` / `capabilities`
5. `exp`（短时过期）
6. `trace_id`

### 5.2 权限级别语义

调用结果统一回传权限级别：

1. `USER_SCOPED`：基于用户身份调用，权限最精确。
2. `TENANT_SCOPED`：第三方仅支持租户级权限，允许降级。
3. `APP_SCOPED`：应用级固定凭据调用，用户级不可验证。
4. `UNVERIFIED`：direct 模式且无法验证完整权限链。

### 5.3 Dify 边界

1. Dify 不负责第三方用户态管理。
2. Dify 不负责行/字段级数据裁剪。
3. Dify 只消费“可调用清单 + 调用结果 + 权限级别标签”。

---

## 6. 调用模式

### 6.1 Gateway 模式（推荐）

1. 智能体调用 `list_available_apis`（网关）。
2. 智能体基于问题选应用与接口。
3. 智能体调用 `invoke_api`（网关）。
4. 网关做鉴权、换票、调用第三方、审计落库、返回结果与权限级别。

### 6.2 Direct 模式（允许）

1. 智能体可直连配置好的第三方接口。
2. 系统必须在配置与返回中标记风险：`permission_level=UNVERIFIED/APP_SCOPED`。
3. 高风险接口建议策略上限制为 Gateway-only（配置层可控，不做强制全局规则）。

---

## 7. 接口管理流程（OpenAPI + 人工确认）

1. 租户管理员先创建应用实例（应用作用、认证类型、调用模式）。
2. 选择“导入 OpenAPI”并解析接口候选。
3. 人工补全并确认：
   - 应用作用
   - 接口作用
   - 风险等级
   - 必需权限/Scope
   - 是否允许智能体调用
4. 生成接口版本快照并生效。
5. 后续导入新版本时做差异对比，人工确认后切换版本。

---

## 8. 智能体工具协议（建议）

### 8.1 工具一：查询可调用接口

`list_available_apis(context, query)`  
返回：

1. 应用列表（含用途、实例信息）
2. 接口列表（含接口作用、参数要求、风险等级）
3. 当前用户可调用标记

### 8.2 工具二：执行接口调用

`invoke_api(context, tenant_app_id, tenant_app_api_id, params)`  
返回：

1. `data`（第三方返回）
2. `permission_level_actual`
3. `call_mode_actual`
4. `trace_id`
5. `warnings`（如降级调用说明）

---

## 9. 可观测与审计

1. 每次调用记录全链路 `trace_id`。
2. 记录调用主体（tenant/user/session）与目标（app/api）。
3. 记录权限级别实际值（是否降级）。
4. 提供租户管理员查询：
   - 最近调用
   - 失败原因分布
   - 高风险接口调用次数

---

## 10. 安全与合规建议

1. 凭据不落明文，统一密文引用（KMS/密钥服务）。
2. Auth Context Token 设短时过期，并绑定 `tenant_id`。
3. 对高风险接口启用参数白名单或模板化参数。
4. 返回体脱敏由第三方负责，但网关需支持日志脱敏（敏感字段不入审计明文）。

---

## 11. 分阶段落地计划

### Phase A：应用管理与接口管理基础

1. 完成 `tenant_app` / `tenant_app_api` / `tenant_app_api_version` 基础模型。
2. 完成“应用实例管理页”与“接口管理页（导入+人工确认）”。
3. 完成 `agent_callable`、`risk_level`、`permission_level` 配置。

验收：

1. 每租户可创建多个应用实例。
2. 每应用可导入接口并人工确认生效。

### Phase B：网关与适配层

1. 完成 Tool Gateway 与 Credential Broker。
2. 完成 OAuth2/API Key/Custom 三类基础适配器。
3. 完成 Auth Context Token 验证链路。

验收：

1. 同一接口可返回 `USER_SCOPED` 或 `TENANT_SCOPED` 标记。
2. 审计日志可追溯到用户与接口。

### Phase C：智能体工具化与路由策略

1. 接入 `list_available_apis` 与 `invoke_api` 两个标准工具。
2. 完成“应用优先 -> 接口选择”提示词与策略。
3. 支持 direct 模式并显式风险提示。

验收：

1. 智能体能基于问题自动选应用与接口。
2. 调用结果带权限级别标签与 trace_id。

### Phase D：运营与治理

1. 调用报表、失败告警、接口健康度。
2. 高风险接口治理策略（Gateway-only 建议策略）。
3. 多环境凭据轮换与过期提醒。

---

## 12. 风险与应对

1. 第三方认证差异过大  
应对：Adapter 插件化，先做 3 类主流认证，再扩展。

2. direct 模式带来权限不透明  
应对：强制标记权限级别与风险，审计上报突出展示。

3. OpenAPI 文档质量参差  
应对：导入后必须人工确认“应用作用/接口作用/权限字段”。

4. 用户态令牌过期或换票失败  
应对：网关统一返回标准错误码，智能体提示用户重新登录或授权。

---

## 13. 本方案结论

本方案在“不强制网关、支持降级、无审批流”的约束下，仍能实现：

1. 租户多应用实例化管理。
2. 接口导入与人工治理并存。
3. 智能体自动路由调用。
4. 第三方权限语义可追踪可解释（通过权限级别标签与审计）。

建议先以 1 个租户 + 1 个应用实例 + 2 个核心接口做 PoC，验证“应用选择准确率 + 权限级别正确率 + 审计可追溯性”后再扩展。

## 16. 联调接口示例（可直接复用）

以下示例基于当前工作空间接口，供联调用：

### 16.1 创建应用

`POST /console/api/workspaces/current/external-apps`

```json
{
  "name": "ERP-华东实例",
  "description": "用于订单与库存查询",
  "app_purpose": "智能体查询订单、库存、发货状态",
  "auth_mode": "oauth2_client_credentials",
  "auth_config": {
    "token_url": "https://example.com/oauth/token",
    "client_id": "tenant-demo-client"
  },
  "is_enabled": true
}
```

支持的 `auth_mode`：

1. `none`
2. `static_bearer`
3. `oauth2_client_credentials`
4. `oauth2_authorization_code`
5. `custom`

### 16.2 创建手工接口

`POST /console/api/workspaces/current/external-apps/{app_id}/apis`

```json
{
  "name": "查询订单详情",
  "http_method": "GET",
  "path": "/api/orders/{orderNo}",
  "summary": "按订单号查询详情",
  "description": "返回订单状态与金额",
  "api_purpose": "客服问答时查询订单状态",
  "required_permissions": ["order.read"],
  "request_schema": {
    "path": {
      "orderNo": "string"
    }
  },
  "response_schema": {
    "status": "string",
    "amount": "number"
  },
  "is_confirmed": true,
  "is_enabled": true
}
```

### 16.3 OpenAPI 导入

`POST /console/api/workspaces/current/external-apps/{app_id}/openapi/import`

```json
{
  "spec": {
    "openapi": "3.0.1",
    "info": {
      "title": "ERP OpenAPI",
      "version": "1.0.0"
    },
    "paths": {
      "/api/orders/{orderNo}": {
        "get": {
          "operationId": "getOrderDetail",
          "summary": "查询订单详情",
          "x-api-purpose": "客服查询订单状态",
          "x-required-permissions": ["order.read"],
          "responses": {
            "200": {
              "description": "ok"
            }
          }
        }
      }
    }
  },
  "overwrite_existing": true,
  "import_as_unconfirmed": true,
  "source_version": 2026041301

```

## 2026-04-21 嵌入式对话口径补充（context_token + 第三方用户隔离）

### 一、最终字段约定（冻结）
1. 会话隔离字段：`systemVariables.user_id`
2. 第三方鉴权字段：`inputs.context_token`

说明：
- 第三方用户隔离只依赖 `user_id` 即可落地。
- `context_token` 用于 Agent/工具调用第三方接口时做权限认证。

### 二、嵌入调用规范
前端嵌入统一采用：

```html
<script>
window.difyChatbotConfig = {
  token: 'YOUR_DIFY_APP_TOKEN',
  baseUrl: 'http://localhost',
  inputs: {
    context_token: 'YOUR_CONTEXT_TOKEN'
  },
  systemVariables: {
    user_id: 'THIRD_USER_ID'
  }
}
</script>
<script src="http://localhost/embed.min.js" id="YOUR_DIFY_APP_TOKEN" defer></script>
```

### 三、工具执行规范
1. Start 节点定义输入变量：`context_token`（string）。
2. 工具入参接收 `context_token`。
3. 下游第三方接口鉴权头：`Authorization: Bearer <context_token>`。
4. 若收到的 `context_token` 已带 `Bearer ` 前缀，运行时需先归一化再拼接，避免重复前缀。

### 四、会话隔离规则
建议会话键：`(app_id, end_user_id)`。
- 其中 `end_user_id` 映射来源为 `systemVariables.user_id`。
- 同一第三方用户在同一 Dify 应用下可复用历史会话；不同用户必须隔离。

### 五、安全边界说明
当前阶段允许“前端直传 context_token”以满足联调与快速接入。
后续推荐升级为“短期 ticket -> 后端换 token”模式，以降低前端暴露长期凭证风险。
