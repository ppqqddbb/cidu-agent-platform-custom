# 第三方应用嵌入式对话通用平台方案（Dify）

## 1. 文档信息
- 文档版本：v1.1
- 更新日期：2026-04-21
- 适用仓库：`D:\workspace\code\dify`
- 目标：改造第三方嵌入式对话调用，支持携带第三方用户信息进行会话隔离，并携带第三方应用 token 用于工具调用外部接口鉴权。

## 2. 核心需求（本次聚焦）
1. 会话隔离：只要第三方用户 ID 即可实现隔离。
2. 第三方接口鉴权：需要携带第三方应用 token，供 LLM 调用第三方接口时直接使用。

## 3. 现状与可复用能力
当前嵌入脚本 `embed.min.js` 已支持通过 URL 参数传递：
- `systemVariables`（会被编码成 `sys.xxx`）
- `userVariables`（会被编码成 `user.xxx`）
- `inputs`（作为应用输入变量）

在 Dify Web 侧：
- `sys.user_id` 可用于映射 `end_user`，用于会话隔离。
- `sys.conversation_id` 可用于指定会话。
- `inputs` 可直接被应用工作流/Agent 读取，适合放第三方 token。

## 4. 方案设计

### 4.1 参数约定
建议统一以下字段：
- `sys.user_id`：第三方用户唯一 ID（必传）
- `sys.conversation_id`：第三方会话 ID（可选）
- `inputs.context_token`：第三方应用 token（必传，用于工具鉴权）
- `inputs.integration_id`：第三方应用标识（可选，建议传）

### 4.2 隔离策略
会话隔离主键建议：
- `(app_id, end_user_id, integration_id)`

最小可行（你当前诉求）可先用：
- `(app_id, end_user_id)`

说明：
- 仅传 `sys.user_id` 即可满足“按第三方用户隔离会话”。
- 若同一用户会接入多个第三方系统，建议再加 `integration_id` 防串会话。

### 4.3 token 传递策略
本方案支持“直接传 token 使用”：
- 第三方前端将 token 放到 `inputs.context_token`。
- Agent 工具从输入变量读取 token，调用第三方接口时拼 `Authorization: Bearer <token>`。

## 5. 端到端流程
1. 第三方页面加载时，拿到当前登录用户 `third_user_id` 与 `context_token`。
2. 写入 `window.difyChatbotConfig`：
- `systemVariables.user_id = third_user_id`
- `inputs.context_token = context_token`
3. 加载 `embed.min.js`，打开 Dify 聊天。
4. 用户发起对话后，工作流/Agent 读取 `context_token`。
5. 工具调用第三方接口时用该 token 鉴权。

## 6. 完整嵌入代码（可直接使用）
```html
<style>
  #dify-chatbot-bubble-button {
    background-color: #1C64F2 !important;
  }
  #dify-chatbot-bubble-window {
    width: 24rem !important;
    height: 40rem !important;
  }
</style>

<script>
  // 这些值由你的第三方业务系统注入
  const thirdUserId = 'user_10086';
  const contextToken = 'YOUR_CONTEXT_TOKEN';
  const thirdConversationId = ''; // 可选，必须是合法 UUID 才建议传

  window.difyChatbotConfig = {
    token: 'D4NMILhVNnrON1Mb',
    baseUrl: 'http://localhost',
    // 可选：内嵌聊天页使用 clean 布局，隐藏顶部栏
    embedLayout: 'clean',
    // 可选：即使传了 conversation_id 也允许“新建对话”
    allowNewChat: true,
    // 可选：窗口支持拖动与拖拽缩放（桌面端）
    windowDraggable: true,
    windowResizable: true,

    // 给工作流 / Agent 工具使用
    inputs: {
      context_token: contextToken,
      integration_id: 'third-system-a'
    },

    // 给 Dify 会话隔离使用
    systemVariables: {
      user_id: thirdUserId,
      conversation_id: thirdConversationId
    },

    // 仅用于前端展示，可选
    userVariables: {
      name: 'Third User',
      avatar_url: ''
    }
  };
</script>

<script
  src="http://localhost/embed.min.js"
  id="D4NMILhVNnrON1Mb"
  defer>
</script>
```

## 7. Agent/工作流侧改造要求
1. Start 节点定义输入变量：
- `context_token`（string，必填）
- `integration_id`（string，可选）
2. 工具入参增加 `context_token`。
3. 调用第三方接口时统一使用：
- Header: `Authorization: Bearer ${context_token}`

## 8. 验收标准
1. 不同 `sys.user_id` 的用户，对话历史互不干扰。
2. 同一 `sys.user_id` 连续访问时可复用历史会话（或按策略新建）。
3. 工具调用第三方接口时可正确鉴权成功。
4. token 失效时工具返回明确错误，并可触发前端重新获取 token。

## 9. 风险与建议
你当前要求“直接携带 token”可以落地，但有以下风险：
- token 暴露在前端页面环境（浏览器插件、XSS、日志采集）

建议后续升级到更安全模式：
- 前端传短期票据（ticket）
- 由第三方后端换取真实 token 后再代理调用

> 结论：本次先按“直接 token 模式”实现，满足业务上线；后续可平滑升级到 ticket 模式。
